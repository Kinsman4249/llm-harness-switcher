## [2.5.0] - 2026-08-23

### Added

- The kilo launcher (`templates/bin/start-local-model-lib.sh`) and the
  ctx-ceiling bench (`bench/ctx-ceiling.sh`) now emit YaRN rope-scaling flags
  from a profile's `ROPE_YARN_*` fields: `--rope-scaling yarn

### Kilo install mode, checked-in templates, model profiles move to presets (round thirty-three)

104. `install.sh` now accepts `--mode classic|kilo`. Classic mode (the default) preserves the LiteLLM switcher exactly as before. Kilo mode installs a new, self-contained flow built around a **single** Kilo Code provider (`local-model`): `start-local-model.sh` scans for local models (GGUFs under `MODEL_ROOT` plus `ollama list`), lets you pick one (or `--profile <stem>`), starts it on its runtime (llama.cpp port 8080 / ollama 11434 / vllm 8000), waits on the runtime's health endpoint, smoke-tests one completion through `/v1`, and then - via `sync-local-model.sh` - rewrites the Kilo provider's one model entry (context, output, reasoning/effort, image modalities for multimodal profiles) to point at exactly the running model. `kilo.jsonc`/`kilo.json` is rewritten atomically (temp file + rename) with only the `provider.local-model` block and top-level `model` pointer touched, preserving the user's other settings; a sqlite-cache reminder tells the user to reload/restart Kilo Code so it re-reads the file. `uninstall.sh` gains matching mode-aware handling via `--classic`/`--kilo`/`--models`/`--all` flags - `remove_classic()` restores any `*.pre-install.bak` backups, and `remove_kilo_config()` (a jq filter) deletes the `provider.local-model` block and nulls the `model` pointer.

### OpenHands launcher fix: silent install failure and missing pip module (round twenty-nine, bugfix)

99. Fixed OpenHands installation hanging indefinitely with no error. Two stacked bugs: (1) the install script piped `distrobox enter ... 2>&1 | tee` for logging, but tested the pipeline's exit status instead of the distrobox command's own exit code, so when `pip install` failed, the `if !` branch saw `tee`'s success and printed "OpenHands installed." anyway, masking the real failure; (2) on Fedora-derived systems, `python3.12` and `python3.12-pip` are separate dnf packages, so even after installing Python 3.12, running `pip install` would error with `No module named pip`. Fixed by: extracting the install command to avoid the piped `if !` and using `${PIPESTATUS[0]}` to check the real exit code, and adding an explicit `dnf install -y python3.12-pip` step if `python3.12 -m pip --version` fails. Both fixes applied to the template in `install.d/80-launcher.sh` (the generated `~/.local/bin/start-openhands.sh` will pick these up on the next `install.sh` run).

### LiteLLM proxy crash-loop fix (round thirty)

100. Fixed `install_litellm_in_container()` in `install.d/40-litellm-and-services.sh` producing a silently-broken proxy on containers with more than one Python interpreter. Root cause, found by live-debugging a real crash-looping proxy (193 restarts): the old check (`python3 -c 'import litellm'`) resolved whatever `python3` was first on PATH, which can be a different interpreter than the one the `litellm` binary itself is shebanged to. On the affected container, `python3` resolved to a Python 3.13 install with litellm's proxy extras present, so the check passed, while the `litellm` binary (what the systemd unit actually runs) was shebanged to Python 3.12, whose litellm copy was missing `apscheduler` (no `[proxy]` extras) - the service crash-looped on every restart, and nothing was ever listening on the proxy port. Fixed by resolving the real interpreter behind the `litellm` binary's shebang before checking or installing, and by checking `litellm.proxy.proxy_server` specifically (not bare `litellm`, which imports fine without the proxy extras) so the check actually exercises the same import the systemd service depends on.

101. Same fix pins `fastapi<0.140` alongside the `litellm[proxy]` install. FastAPI 0.140.4 (released 2026-07-27) removed `get_flat_dependant()`, a function litellm's proxy server still imports at startup; litellm's own declared dependency range (`fastapi>=0.136.3,<1.0`) is loose enough that a plain `pip install litellm[proxy]` can pull in the broken release and fail with an unrelated-looking `ImportError` on startup. This is a workaround for that upstream gap, not a formal litellm requirement, and should be revisited once litellm tightens its own pin or fixes the import.

### Qwen3.5-9B speed optimization via KV cache quant benchmarking (round twenty-seven)

89. Added comprehensive benchmarking harness in `bench/` (qwen-bench.sh, build_haystack.py, query_and_grade.py, query_and_grade.py, run-phase2.sh) to sweep KV cache quant combinations and CPU-resident FFN layer counts at fixed 131072-token context. Full raw results committed to bench/qwen-results.md. The sweep revealed that asymmetric KV cache types (q8_0/q5_1, q8_0/q4_0, q5_1/q5_1) collapse onto a catastrophically slow non-fused CUDA path on this project's llama.cpp build (plausibly due to GGML_CUDA_FA_ALL_QUANTS=OFF), while symmetric q8_0/q8_0 and q4_0/q4_0 stay fast. q4_0/q4_0 uses ~1GB less VRAM at the same layer count with no quality difference, which funds dropping CPU-resident FFN layers from N=24 to N=11. Measured at ~99870 tokens: prefill +21.0% (1019.2 -> 1233.5 tok/s), decode +59.8% (24.57 -> 39.26 tok/s), quality still passes 3/3 sentinels + correct code generation. Thread count made no measurable difference once CPU layers dropped to 11.

### Switch to llama-server, context math, and VRAM headroom controls (round eight)

26. Replaced Ollama with `llama-server` (llama.cpp's native HTTP server) as the local runtime. Ollama lacked support for `--n-cpu-moe` (MoE expert layer offload), generic speculative decoding, and fine-grained VRAM-tuning flags that the user requested. The switch is transparent on upgrade: existing installs just re-run `install.sh`, which handles all the config migration (LiteLLM backend URL changes from Ollama's port 11434 to llama-server's port 8080, wrapper script generation with new flags, etc.) without manual file editing.
27. Corrected the architecture description of Qwen3.5-9B after reading its actual config.json: it is a **hybrid dense model with no MoE layers at all**, not a "hybrid dense+MoE" as earlier docs claimed. Of its 32 layers, only every 4th one (8 total) is full quadratic attention; the other 24 are linear/DeltaNet attention with a small fixed-size recurrent state that does not grow with context length. This architectural detail matters for VRAM math and CPU-offload tradeoffs (see below).
28. Implemented context-length recommendation math in `install.sh` based on the KV-cache formula for this specific model: `bytes/token = 2 (K+V) × 4 (num_kv_heads) × 256 (head_dim) × 8 (full-attention layers) × 1 (q8_0) = 16 KiB/token`. After the user picks a quant and batch size, `install.sh` now estimates `usable_VRAM - quant_weight_size - estimated_compute_buffer - overhead`, converts to tokens, applies a 15% safety margin, and pre-fills the context-length prompt with a recommendation (user can accept or override). The compute-buffer estimate scales from a community report (~1508 MiB at batch 2048), underscoring why batch size matters: at batch 2048, the compute buffer alone can consume most of the headroom a ~7-8 GB card has after a Q5-class quant.
29. Changed batch-size default from 2048 to 512 (llama.cpp's own default) based on the above: batch 2048's compute buffer was leaving almost no room for KV cache, reproducing the "out of context" symptom the user reported. The prompt now explains the tradeoff (larger batch = more prompt-processing throughput but less room for context) and lets the user decide; the context math re-runs dynamically based on whatever they pick.
30. Enabled flash attention (`-fa on`) and Q8 KV-cache quantization (`--cache-type-k q8_0 --cache-type-v q8_0`) by default in the generated `start-local-llama.sh` wrapper. Flash attention is required for KV-cache quantization to work and improves both quality and VRAM efficiency; Q8 approximately halves KV-cache memory vs. the default FP16.
31. Enabled speculative decoding via the MTP (Multi-Token Prediction) head built into the `unsloth/Qwen3.5-9B-MTP-GGUF` model (`--spec-type draft-mtp --spec-draft-n-max 2` by default). MTP achieves ~1.5-2x faster generation by allowing the model to predict multiple tokens ahead; the community-recommended draft-token count for dense models is 2 (higher for MoE, but this model is dense).
32. Added `--override-tensor` (CPU FFN offload) support with a conservative default: 2 of the last 32 layers' FFN weights are offloaded to CPU RAM by default. The underlying technique is the same as `--n-cpu-moe` on MoE models (use CPU for large tensors to free VRAM), but dense FFN tensors have a significantly higher per-token cost: each offloaded layer's entire dense FFN matrix (three 4096×12288 matrices) gets read from RAM on every single token, every time, adding on the order of 2–3 milliseconds per token per offloaded layer (at ~40 GB/s typical RAM bandwidth). A community guide to this technique explicitly recommends against FFN offloading for dense models and reserving the trick for MoE experts (where only 1-2 activate per token). The conservative default (2 layers) offers a small VRAM win without a noticeable latency cost; raising it trades speed for more room, useful only if a smaller quant isn't enough and context length is critical. The prompt explains this tradeoff and suggests a smaller quant as the better lever for fast, Haiku-replacement-style workloads.
33. Added `--no-kv-offload` (system-RAM KV cache) as an opt-in feature, default off, with an explicit performance warning. This decouples context length from VRAM almost entirely (bound by system RAM instead), but imposes an ongoing per-token latency cost for the entire session (not just once at load): every attention step moves cache data over PCIe to system RAM and back. Not yet confirmed clean on all backend/model combinations; there are reported issues with some Vulkan-model pairings producing broken output. The prompt warns against this upfront and recommends it only when VRAM context length is the bottleneck and session speed is acceptable.
34. Replaced the manual `ollama serve` terminal-launch flow with a dedicated desktop icon ("Start Local Model") that opens `start-local-llama.sh` in its own terminal window (`konsole`, falling back to `gnome-terminal` or `xterm`), with an automatic fallback to a copy-paste notification if no terminal emulator is found. This makes day-to-day server startup a single double-click instead of typing a command.

This covers ambiguous typos and prevents a false "not found" error; the chosen container name is saved as the new default, so re-runs use the corrected name without prompting again.

26. Fixed the automatic `ollama serve` startup from round seven still failing with the same `could not connect to ollama server` error on a subsequent run. The previous check used `pgrep -f 'ollama serve'` to decide whether a server was already running, which can match a stale or crashed process that still appears in the process table but is no longer actually listening, causing the script to skip starting a working server and fail later with a confusing connection error at the `ollama create` step instead. ### Ollama server startup moved to a visible terminal window (round nine)

27. Fixed `ollama serve` continuing to fail to stay up even after round eight's improved detection, root-caused to backgrounding it with `nohup`/`disown` inside a `distrobox enter -- bash -lc "..."` session in the first place: container runtimes can tear down every process spawned inside a given exec session once that session's own command exits, independent of `nohup`, so the server process was being killed the moment the download/build subshell finished, regardless of how well its presence was checked afterward. Replaced backgrounding entirely with opening `ollama serve` in its own terminal window (`konsole`, falling back to `gnome-terminal` or `xterm` if konsole isn't present), which keeps the process alive in a session the script never tears down, and doubles as the requested visibility into the server's own output for monitoring. The window stays open even if `ollama serve` exits or crashes, pausing on a keypress, so an error is visible instead of the window disappearing. The check for whether a server is already running, and the subsequent wait for a freshly opened one, both curl `http://localhost:11434/api/tags` directly from the host rather than entering the container, since Distrobox containers share the host's network namespace by default and the port is already reachable without an `enter`. If no supported terminal emulator is found, or the server still isn't reachable after 30 seconds, the download and build step is skipped with a clear message rather than proceeding into a step that would fail anyway; every other step in the script still runs normally.

### CUDA toolkit installation fix (round eleven)

29. Fixed `install.sh` failing to build `llama-server` from source inside a Fedora 41 Distrobox container with `ERROR: nvcc still not available after attempting install`, which surfaced when attempting a fresh build after switching from Ollama to llama.cpp. Root cause: Fedora's own package repositories do not carry `cuda-toolkit` at all  -  it only exists after NVIDIA's own per-version CUDA repository is added. The bare `sudo dnf install -y cuda-toolkit` command was failing silently (marked `|| true`) because the package was simply not available, and neither error message nor retry logic surfaced the missing-repo issue. Additionally, even after successfully installing `cuda-toolkit` via NVIDIA's repo, the `nvcc` binary was not on `PATH` in the same subshell (it requires a fresh login shell to source CUDA's profile.d hook), causing the existence check to still fail. The fix adds three changes to the build subshell: (1) detect the container's Fedora version by reading `/etc/os-release`; (2) probe for the existence of NVIDIA's matching CUDA repository using `curl -fsI` against `developer.nvidia.com/compute/cuda/repos/fedora<N>/...` and add it via `dnf config-manager addrepo --from-repofile=` if not already installed, with a fallback error if NVIDIA has no published repo for that Fedora version yet; (3) export `/usr/local/cuda/bin` to `PATH` at the start of the build subshell so `nvcc` becomes usable immediately after install in the same shell session, without needing a new login. Tested end-to-end against a Fedora 41 container to confirm the CUDA repo URL is reachable, the `cuda-toolkit` package becomes available once the repo is added, and `nvcc` is correctly found on PATH afterward.

### llama-server startup reliability (round thirteen)

33. Fixed `start-local-llama.sh` firing a misleading `common_fit_params: ... abort` warning on every startup. The underlying cause is llama.cpp's automatic VRAM-fitting pass (`--fit`, enabled by default), which runs before the manual layer-offload budget (`-ngl 99`) and cannot override it. Since `-ngl 99` already requests all layers to VRAM, the fitting pass cannot reduce layer counts to fit the result into the requested budget, and triggers an abort warning that looks like a failure even though actual inference works fine. Fixed by explicitly disabling the fitting pass (`--fit off`) when a manual offload budget is already specified, eliminating the harmless but alarming-looking warning and making the startup log cleaner. See https://github.com/ggml-org/llama.cpp/discussions/18049 for upstream discussion.

This prevents resource conflicts and silent failures from port binding.

This is an llama.cpp behavior edge case: the `--fit` automatic-sizing only works when both `-ngl` and `-c` are left completely unset; an explicit `-c` is always treated as a fixed hard ceiling, never as a suggested value `--fit` is free to reduce. Testing with `--fit on` and both values unset (no `-ngl`, no `-c`) against the largest quant showed llama-server automatically selected 92416 tokens and successfully served completions. Documenting this exact value as `RECOMMENDED_CTX_8GB=92416` for the 4B profile, with inline notes explaining why the model's metadata maximum wasn't usable as-is.
